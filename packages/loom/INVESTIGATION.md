# Loom investigation

The user selected TanStack Query core with its official React adapter, a ClerkJS-free core with host ClerkJS browser transport, and an explicit Loom boundary. The browser boundary now subscribes directly to a concrete ClerkJS host without ClerkProvider. The original Mosaic compatibility route remains at `/loom/legacy` because that component still uses Clerk React hooks for reverification. Development-instance SSR was verified against staging through the earlier credential experiment. The new BAPI server path is implemented locally but not deployed; production SSR and credential rotation remain unresolved.

Source baseline: `e8a03c96006c4af3893e4e5717602c5805c2422f`. Existing ClerkJS and Mosaic production implementations remain unchanged; the Backend SDK now has one additional session read method. The committed [characterization probes](research/) preserve the initial transport evidence. See [README](README.md) for the implemented contract, verification commands, and limitations.

## Existing operation

The Mosaic model waits for user and session readiness, then calls `currentUser.getSessions()`. It uses user ID plus session ID to reject late results. It filters active and pending sessions, puts the current session first, formats device labels and dates, and wraps revocation in reverification. [packages/mosaic/src/features/user-profile/user-profile-active-devices-section/user-profile-active-devices-section.model.ts](../mosaic/src/features/user-profile/user-profile-active-devices-section/user-profile-active-devices-section.model.ts#L42).

`User.getSessions()` caches its first resolved array on the resource, including an empty array returned after a failure. Its retrieval calls `GET /me/sessions/active` directly and converts any rejection or mapping exception to `[]`. [packages/clerk-js/src/core/resources/User.ts](../clerk-js/src/core/resources/User.ts#L333), [packages/clerk-js/src/core/resources/SessionWithActivities.ts](../clerk-js/src/core/resources/SessionWithActivities.ts#L39).

The FAPI client adds the current session ID and API version, chooses proxy or domain routing, uses host request/response callbacks, includes cookies by default, and retries network failures. It returns non-2xx responses rather than throwing. The supplied session ID is replaced by the host's current session ID. A direct read can bypass the resource cache, but must validate HTTP status and the endpoint's bare array payload. [packages/clerk-js/src/core/fapiClient.ts](../clerk-js/src/core/fapiClient.ts#L139), [packages/clerk-js/src/core/fapiClient.ts](../clerk-js/src/core/fapiClient.ts#L250), [packages/clerk-js/src/core/fapiClient.ts](../clerk-js/src/core/fapiClient.ts#L328).

Normal resource operations add error conversion, selected 401 recovery, retry-after metadata, and client updates. Direct sessions retrieval bypasses that layer today. Reusing the transport therefore preserves its hooks, not every behavior of `BaseResource`. A Loom integration must specify HTTP error conversion and host recovery explicitly. [packages/clerk-js/src/core/resources/Base.ts](../clerk-js/src/core/resources/Base.ts#L94).

`getFapiClient()` exists on the concrete ClerkJS class. React's `IsomorphicClerk` and the shared Clerk interface do not expose it. A standalone browser can create and load ClerkJS, then pass that instance to Loom without ClerkProvider. Chromium tests exercise this direct path and preserve separate real ClerkProvider compatibility tests with MSW responses. [packages/clerk-js/src/core/clerk.ts](../clerk-js/src/core/clerk.ts#L604), [packages/react/src/isomorphicClerk.ts](../react/src/isomorphicClerk.ts#L597).

`client.sessions` is the current client's session resources. The active-device endpoint returns sessions with latest activity for the signed-in user. They are different datasets. [packages/clerk-js/src/core/resources/Client.ts](../clerk-js/src/core/resources/Client.ts#L142), [packages/shared/src/types/json.ts](../shared/src/types/json.ts#L357).

Revocation posts to `/me/sessions/{id}/revoke`. Mosaic currently hides the removed row using controller-local IDs. That does not invalidate every consumer of the User resource's cached array. Reverification recognizes a structured Clerk error and retries after verification. [packages/clerk-js/src/core/resources/SessionWithActivities.ts](../clerk-js/src/core/resources/SessionWithActivities.ts#L57), [packages/mosaic/src/features/user-profile/user-profile-active-devices-section/user-profile-active-devices-section.controller.ts](../mosaic/src/features/user-profile/user-profile-active-devices-section/user-profile-active-devices-section.controller.ts#L40), [packages/shared/src/react/hooks/useReverification.ts](../shared/src/react/hooks/useReverification.ts#L108).

## Library evidence

TanStack's documented freshness, inactive-cache lifetime, retries, and structural sharing cover the general query mechanics. The prototype sets these explicitly. Loom uses a 30-second freshness window and disables query retries so transport retries are not multiplied. These values are experiment defaults, not measured requirements. [Important defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults).

The installed core is `5.102.8`, resolved from the workspace catalog range `^5.101.4`. Source `queryClient.ts:392–434` checks freshness and makes `prefetchQuery` swallow promise errors while retaining query error state. Source `query.ts:400–415` shares an in-flight promise. The probes demonstrate both behaviors. [node_modules/.pnpm/@tanstack+query-core@5.102.8/node_modules/@tanstack/query-core/src/queryClient.ts](../../node_modules/.pnpm/@tanstack+query-core@5.102.8/node_modules/@tanstack/query-core/src/queryClient.ts#L392), [node_modules/.pnpm/@tanstack+query-core@5.102.8/node_modules/@tanstack/query-core/src/query.ts](../../node_modules/.pnpm/@tanstack+query-core@5.102.8/node_modules/@tanstack/query-core/src/query.ts#L400).

Cancellation is useful but not the ownership contract. An unused query can finish and populate its cache. The experiment shows that a plain cache write after a revoke does not stop an earlier response from restoring the row. [Cancellation](https://tanstack.com/query/latest/docs/framework/react/guides/query-cancellation).

The official React binding supplies Suspense and error-boundary reset. Its Suspense hook cannot be conditionally enabled, so readiness belongs outside the mounted query consumer. By default a refresh failure with existing data does not replace the list with an error boundary. [Suspense](https://tanstack.com/query/latest/docs/framework/react/guides/suspense).

Request-local clients and successful-query dehydration are established mechanisms. They do not provide credentials. The initial probe checked a query-cache JSON round-trip. Loom now also has Node renderToString isolation tests and a DOM hydrateRoot test that verifies matching markup without refetching. These tests use controlled transports. Applications must use safe framework serialization for inline data. [Server rendering and hydration](https://tanstack.com/query/latest/docs/framework/react/guides/ssr).

SWR contributes a useful ownership warning. Its global mutate does not reach a custom provider's cache. RTK Query proves React independence through dispatch, selectors, and explicit unsubscribe, but requires Redux ownership. Neither removes Clerk's transport problem. [SWR cache](https://swr.vercel.app/docs/advanced/cache), [RTK Query without React](https://redux.js.org/toolkit/rtk-query/usage/usage-without-react-hooks).

## Runtime ownership

LoomProvider owns one Loom client at a time. Plain JavaScript callers create and dispose their own clients. Multiple consumers inside one boundary share an operation. Separate LoomProvider boundaries own isolated caches, even if their Clerk runtime is shared. The public React API does not expose cross-root owner sharing. Plain JavaScript callers can share a client explicitly.

Cache isolation does not prove mutation isolation. ClerkJS's BaseResource.clerk is static in browsers too, and resource revocation uses it. The demo shares one host runtime. Loom calls the captured host transport for reads and revocation, checking its scope before and after dispatch; it never uses the resource static. Distinct simultaneous ClerkProvider runtimes remain unverified because the existing React wrapper has its own singleton constraints.

React rejects nested Clerk providers but permits separate roots. Its browser `IsomorphicClerk` is cached statically, while server creation is per call. The provider stores its instance in a ref and clears the static instance on effect cleanup. The direct Loom boundary does not use that wrapper; controlled tests replace its host with the same IDs and verify both listener channels are removed. The Mosaic compatibility route still follows the existing provider lifecycle. [packages/react/src/contexts/ClerkProvider.tsx](../react/src/contexts/ClerkProvider.tsx#L30), [packages/react/src/contexts/ClerkProvider.tsx](../react/src/contexts/ClerkProvider.tsx#L62), [packages/react/src/isomorphicClerk.ts](../react/src/isomorphicClerk.ts#L222).

Initial SSR state feeds shared auth/resource hooks until live Clerk resources are ready. Loom now reads readiness and identity only from its concrete ClerkJS host. The React boundary renders a validated hydration snapshot without starting transport. Its live binding still waits for the concrete host. [packages/shared/src/react/contexts.tsx](../shared/src/react/contexts.tsx#L15), [packages/react/src/hooks/useAuthBase.tsx](../react/src/hooks/useAuthBase.tsx#L40).

Shared React code has a browser-only singleton QueryClient. ClerkJS retains a separate lazy query-client compatibility shim. The shared implementation deliberately keeps its Observer and Query objects in the same bundle resolution. Loom should own its client and matching observers instead of borrowing either existing client. No existing hooks migrate in this slice. [packages/shared/src/react/query/clerk-query-client.ts](../shared/src/react/query/clerk-query-client.ts#L3), [packages/clerk-js/src/core/clerk.ts](../clerk-js/src/core/clerk.ts#L307).

## Server authentication evidence

React's server provider supplies auth state without a loaded browser runtime. The inspected FAPI request relies on host callbacks and fetch credentials. A server `credentials: 'include'` option does not itself supply the incoming user's Clerk client credentials. The controlled transport probe records no Cookie or Authorization header without a host hook.

Backend `getSessionList` calls administrative `/sessions`, and backend `getToken` does not prove that its token authorizes the FAPI sessions endpoint. The repository has a FAPI proxy that forwards incoming headers, but production credentials, rotation, and verification behavior remain unproven. The development path below calls FAPI directly. [packages/backend/src/api/endpoints/SessionApi.ts](../backend/src/api/endpoints/SessionApi.ts#L47), [packages/backend/src/tokens/authObjects.ts](../backend/src/tokens/authObjects.ts#L193), [packages/backend/src/proxy.ts](../backend/src/proxy.ts#L273).

`BaseResource.clerk` is module-static and assigned by Clerk construction. It is unsuitable as request-local server ownership. [packages/clerk-js/src/core/resources/Base.ts](../clerk-js/src/core/resources/Base.ts#L66), [packages/clerk-js/src/core/clerk.ts](../clerk-js/src/core/clerk.ts#L599).

The initial SSR blocker was the missing end-user credential path to FAPI. The two probes below distinguish a failed session-token path from a working development browser credential.

A live staging probe on 2026-10-21 at 03:41 UTC tested the simplest proposed credential path. It created a disposable session for the dedicated test user, minted its session JWT, then sent that JWT as a Bearer token to `/v1/me/sessions/active` with the session selector. FAPI returned HTTP 401 with `signed_out`. The test session was revoked afterward. This rules out that direct session-token request on the tested staging instance; it does not rule out every server transport. No tokens were logged or serialized.

A second live probe on 2026-10-21 at 05:15 UTC verified the development browser credential path. The Next server authenticated the incoming request, extracted its suffixed development cookie, verified the exact user/session through `/client`, and read `/me/sessions/active`. Both FAPI requests returned 200. The actual Active devices page contained the device name and current-device marker in HTML after scripts were removed. The response was `no-store, must-revalidate`.

The browser then bound the existing ClerkJS instance to the same scope without an initial Loom GET. Explicit Refresh produced one GET. Temporary transport logging contained only the method/path and match boolean and was removed after the check. The diagnostic route was also removed.

`prefetchDevelopmentSessions` implements only this historical development-instance path. It restricts FAPI hosts, forbids redirects and caching, checks both the authenticated client identity and selected session in the result, and sanitizes failures. The provider renders a read-only snapshot first, then transfers it once to an exact-match live owner.

The current live page uses `@clerk/loom/nextjs`. It takes the verified user/session from `auth()`, uses the request-aware Backend API client, resolves browser routing through Next middleware's encrypted request data, and calls `SessionAPI.getActiveDevices`. The SDK sends the application secret through its usual transport, refuses redirects and shared fetch caches for this operation, and forwards an abort signal. The shared `@clerk/loom/server` operation validates the returned subject's user/session, projects the minimal device shape, and dehydrates a request-local owner. Next only passes its authenticated identity and lazy client/routing resolver. Other SDK adapters can reuse this operation with their existing request authentication and configuration. The returned instance ID is required but cannot be compared with an independent instance ID from `auth()`, which does not expose one. Backend secret-key authentication and instance-scoped session lookup provide the instance binding.

This new endpoint is not deployed. A missing route or the backend's explicit 1000-candidate limit produces a failed server read and the live page's browser-loading fallback. The earlier staging SSR observation does not verify this BAPI route, production response-cache headers, or credential rotation.
