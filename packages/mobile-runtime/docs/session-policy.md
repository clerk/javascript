# Session policy across generated native APIs

Session behavior is implemented in the shared TypeScript core. Generated calls preserve its option meanings and errors; native hosts do not recreate the old native service or token cache.

Explicit organization activation must report a rejected request. The general authentication-error handler previously swallowed 401 responses from session touch, refreshed the client, and allowed `setActive` to finish successfully without activating the requested organization. Explicit organization selection now propagates that rejection through both ordinary and navigation touch paths. Background touches retain their existing recovery behavior. The underlying request layer can still refresh the client before returning a structured 401 error.

`session-activation.test.mjs` proves 401/403 status and code delivery, preservation of the prior organization and its template token after rejection, accepted selection, explicit personal selection, omitted organization, forced organization selection, and a pending rejected request racing with a newer accepted selection. A retained session reads a different template cache entry after an accepted organization change. Cache partitioning, rather than a native helper's deletion timing, prevents use of the previous organization's token.

`session-token-policy.test.mjs` checks actual generated HTTP requests for first mint, forced first mint, an existing token with forced origin, disabled session minter, and a template request. `skipCache` can force origin on the first mint when session minter is enabled. Template requests omit organization, previous token, force-origin, and tab-state form fields. Default requests carry the shared lifecycle-derived tab state. A nonselected session that remains in `Clerk.sessions` supports coalesced token requests and cache hits without changing selection.

`session-sign-out.test.mjs` checks all-session and scoped sign-out, successful and rejected requests, stale handles, and subsequent token reads. Canonical `Session.remove` clears the entire token cache before HTTP, including other sessions' entries and failed requests. Canonical `Client.removeSessions` clears it after success; a 500 response preserves cached tokens. Both forms invalidate old generated handles at authentication reset. These are intentional differences from the old Swift service's scoped, success-only cache removal, not additional native algorithms. Callers reacquire resources from the current Clerk state after reset.

These checks use the real packaged core with deterministic host responses. They establish request construction and observable client behavior, not live service acceptance, physical-device performance, or signed-in upgrades from a released native SDK.
