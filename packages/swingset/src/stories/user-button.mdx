# UserButton

The account & organization switcher behind the user avatar. The active organization heads the surface,
badged with the account, carrying **Settings** and **Invite**. The account's organizations sit under it: every one it belongs to, plus
**suggested** and **invited** ones it can Join. **Switch account** at the foot opens the signed-in
accounts as a flyout — the active one checked — so an account never reads as an organization. The
flyout also adds an account and signs out of all of them. With nobody to switch to, that row is
**Add account** instead. The foot signs out of the active account. `mode` narrows all of it;
see [Modes](#modes). For organizations alone, use `OrganizationSwitcher`.

Only the active account's organizations are listed. Not a design choice: org requests are scoped to
the session that makes them, so another account's organizations are unknowable until it _is_ active.
Hence `additionalSessions` carries sessions alone, and `onSelectOrganization` takes no session.

Composed from `Popover`, `Card`, `Item`, `Avatar`, and `Menu`, so behavior, focus, and ARIA come from
them rather than being restyled. `SwitcherView` is presentational; the connected `UserButton` wraps
it with `useSwitcherController()` and needs no props.

## Example

A working prototype over mock accounts — try it. Nothing is instant: the clicked row spins, the rest
stand down, and the surface stays open so you land on the result. Only picking an organization closes it.
`pendingKey` drives that, and the connected `UserButton` sets it from the action in flight. Actions
that would navigate (Manage, Invite, Create organization, Add account) only close the popover here.

## Usage

`SwitcherView` renders trigger and popup from one prop-driven call:

```tsx
import { SwitcherView } from '@clerk/mosaic/features/switcher/switcher.view';

<SwitcherView
  activeSession={{ sessionId: 'sess_1', name: 'Cameron Walker', identifier: 'cameron@clerk.com' }}
  activeOrganization={{ kind: 'membership', organizationId: 'org_nestlabs', name: 'NestLabs Creative', membersCount: 24, planLabel: 'Pro plan' }}
  hasOrganizations
  memberships={[
    { kind: 'membership', organizationId: 'org_nestlabs', name: 'NestLabs Creative', membersCount: 24, planLabel: 'Pro plan' },
    { kind: 'membership', organizationId: 'org_acme', name: 'Acme' },
  ]}
  suggestions={[{ kind: 'suggestion', id: 'sug_clerk', organizationId: 'org_clerk', name: 'Clerk', status: 'pending' }]}
  invitations={[]}
  additionalSessions={[{ sessionId: 'sess_2', name: 'Cameron Walker', identifier: 'cameron@clerk.com' }]}
  onSelectOrganization={organization => setActive({ organization })}
  onSwitchSession={session => setActive({ session })}
  onSignOutAll={() => signOut()}
/>
```

To drop the popup into your own trigger, compose the parts. Data and callbacks live on
`SwitcherRoot`; the leaves read them from context:

```tsx
import {
  SwitcherRoot,
  SwitcherTrigger,
  SwitcherPopup,
} from '@clerk/mosaic/features/switcher/switcher.view';

<SwitcherRoot {...data} {...callbacks}>
  <SwitcherTrigger />
  <SwitcherPopup />
</SwitcherRoot>
```

Exports are flat (not `UserButton.Trigger`) so each part declares its own `'use client'` boundary.

## Trigger

The avatar and name of whatever leads the popup. With an organization active, it leads with the
organization, badged with the account, and names the account's identifier beneath it.

`renderTriggerLabel={false}` leaves the avatar alone. A user's avatar on its own rounds the trigger
fully to match it; see [User only](#user-only).

## Header

The header names whatever leads and carries what you can do about it, stacked under it as
full-width labelled buttons. An organization is described by its plan and member count, and carries
**Settings** with **Invite**. An account is described by its identifier, and so is an organization the account badges. Where **Settings** is the only
action, as it is for an account, it trails the account inline.

With an organization active in `combined`, **Settings** opens a menu of **Organization settings** and
**Profile settings**. Where only one of them is available, **Settings** opens it directly.

## Modes

`mode` picks which switchers the surface carries — the only prop that changes the popup's shape.
Everything else is data.

| Mode                 | Popup                                | Leads with                               |
| -------------------- | ------------------------------------ | ---------------------------------------- |
| `combined` (default) | Organizations and accounts together. | The active org, badged with the account. |
| `user`               | Accounts only; never shows an org.   | The account.                             |

What a mode leads with is named in the trigger and heads the popup — the two always agree.

## Loading

Memberships, invitations and suggestions are three separate requests, and the popup opens before any
of them land. `organizationsLoading` holds the organization list's place until the last one is in — one
placeholder for all three, so the list does not walk itself in a row at a time. The header is
already known, so it renders throughout.

## Single session

An instance in single-session mode holds one account at a time, so there is nothing to switch to and
no second account to add. It hands the view an empty `additionalSessions` and leaves `onAddAccount`
and `onSignOutAll` off — the surface withholds **Switch account**, **Add account**, and **Sign out of
all accounts**. The foot keeps **Sign out**.

## Menu items

`customMenuItems` adds the app's own rows to the foot of the popup, ahead of Clerk's own. A row with
`onClick` is an action and closes the popup on the way out; a row with `href` is a link and navigates
on its own, so it stays followable while another action is in flight. The `icon` is optional — a row
without one still holds the column, so labels stay in line.

`menuItemOrder` names the foot's rows by id, and whatever it leaves out follows what it named. The
ids it knows are `switchAccount`, `addAccount`, `signOut`, and each custom item's `id`.
Those are the only actions the foot lists as rows; the rest live in the header or with the organizations, where there is no list for an order to run in.

In `combined`, the accounts row is `switchAccount` where there is somebody to switch to and
`addAccount` where there is not. Name both ids to place a row whichever way it resolves. An id the surface has not got
is ignored rather than an error, so one order can cover every mode.

## Parts

| Part              | Description                                                                      |
| ----------------- | -------------------------------------------------------------------------------- |
| `SwitcherRoot`    | Owns the data, callbacks, and `mode`; forwards open state to `Popover.Root`.     |
| `SwitcherTrigger` | The trigger: the active account or organization's avatar, and what it is called. |
| `SwitcherPopup`   | The popover surface: header, organization list, footer.                          |
