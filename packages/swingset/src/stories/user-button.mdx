# UserButton

The account & organization switcher that sits behind the user avatar. The account you're signed in as
heads the surface — the one large row, carrying a **gear** that manages it and, where an organization
is active, an **Invite** button. Under it sit that account's workspaces: every organization it
belongs to, and any **suggested** or **invited** workspaces it can Join. The account's own `⋯` menu
carries its per-account actions. Every _other_ signed-in account sits below that under
its own **Accounts** heading — plain rows you click to switch to, with **Add account** on the
heading's `⋯` — so an account is never mistaken for a workspace. The foot of the surface signs you
out of everything. `mode` narrows all of this to just the organizations or just the accounts; see
[Modes](#modes).

Only the active account's organizations are listed, and that is a data constraint rather than a
design one: organization requests are scoped to the session that makes them, so another account's
workspaces are unknowable until it _is_ the active one. That's why `additionalSessions` carries
sessions alone, and why `onSelectOrganization` takes no session — it can only ever mean the active
one.

It is a composition of lower-layer Mosaic components — `Popover` for the floating surface, `Card` for
the surface itself, `Item` for every row, `Avatar` for the workspace marks, and `Menu` for the
per-account actions — so it inherits their behavior, focus management, and ARIA wiring rather than
restyling any of it. `UserButtonView` is presentational: the parts render from the props on
`UserButtonRoot` (mock data in the examples). The connected `UserButton` wraps it with
`useUserButtonController()`, which reads live Clerk resources and needs no props.

## Example

Every example on this page is a working prototype over the same mock accounts, so try it:
picking a workspace or an account switches to it, **Join** turns a suggested workspace into one
you're in, and the trigger updates to whatever is active. The actions that would navigate somewhere
in a real app — Manage, Invite, Create organization, Add account — have nowhere to go here, so they
only close the popover.

None of it is instant. Every switch is a request against Clerk, so the prototype fakes the round
trip the connected component really makes: the row you clicked spins, the rest stand down until it
settles, and the surface stays open so you land back on the result. Picking a workspace is the
exception — it is the one thing the surface exists to do, so it closes behind you. `pendingKey`
is what drives that: the view marks the affordance whose key matches busy and disables the others,
and the connected `UserButton` sets it from the action in flight.

## Usage

The all-in-one, presentational `UserButtonView` renders the trigger and popup from a single
prop-driven call (the connected, Clerk-backed `UserButton` wraps it and needs no props):

```tsx
import { UserButtonView } from '@clerk/ui/mosaic/user-button/user-button.view';

<UserButtonView
  activeSession={{ sessionId: 'sess_colin', name: 'Colin', email: 'colin@clerk.dev' }}
  activeOrganizationId='org_clerk_app'
  hasOrganizations
  memberships={[
    { kind: 'membership', organizationId: 'org_clerk_app', name: 'Clerk app', membersCount: 24, planLabel: 'Pro plan' },
    { kind: 'membership', organizationId: 'org_clerk_cloud', name: 'Clerk Cloud' },
  ]}
  suggestions={[{ kind: 'suggestion', id: 'sug_labs', organizationId: 'org_clerk_labs', name: 'Clerk Labs', status: 'pending' }]}
  invitations={[]}
  additionalSessions={[{ sessionId: 'sess_braden', name: 'Braden', email: 'braden@clerk.dev' }]}
  onSelectOrganization={organization => setActive({ organization })}
  onSwitchSession={session => setActive({ session })}
  onSignOutAll={() => signOut()}
/>
```

For layouts that need to drop the popup into their own trigger, compose the parts directly. The data
and callbacks live on `UserButtonRoot` and are read from context by the leaves, so they take no props:

```tsx
import {
  UserButtonRoot,
  UserButtonTrigger,
  UserButtonPopup,
} from '@clerk/ui/mosaic/user-button/user-button.view';

<UserButtonRoot {...data} {...callbacks}>
  <UserButtonTrigger />
  <UserButtonPopup />
</UserButtonRoot>
```

The exports are flat (not `UserButton.Trigger`) so each part can declare its own `'use client'`
boundary without forcing the consumer's file to become a client component.

## Modes

`mode` picks which switchers the surface carries. It is the only prop that changes the shape of the
popup; everything else is data.

| Mode                 | Popup                                | Trigger          | Header      |
| -------------------- | ------------------------------------ | ---------------- | ----------- |
| `combined` (default) | Organizations and accounts together. | The org's mark   | The account |
| `orgs`               | Organizations only; no account rows. | The org's mark   | The org     |
| `user`               | Accounts only; never shows an org.   | The user's photo | The account |

The trigger follows whichever organization is active, which is why `combined` and `orgs` both land
on the org's mark; `user` never resolves to an organization, so it shows the account's photo even
when one is active.

Only `orgs` is _headed_ by the organization. Everywhere else the account heads the surface, so
switching organization changes the trigger and the check in the list without changing who the popup
says you're signed in as. **Invite** still belongs to the active organization wherever there is one,
which is why it sits next to an account in `combined`; the gear manages whatever the header names.

Passing organization data in `user` mode, or extra sessions in `orgs` mode, is not an error — the
mode decides what renders, so a single set of props can drive any of the three. The two examples
below prove it: they take exactly the same props as the one above, and differ only by `mode`.

### Organizations

The org is the header, carrying **Invite** and the gear (**Manage organization**). With no account
menu to hold it, **Create organization** moves to the foot of the surface. The other signed-in
account is still in the props and is deliberately not rendered.

### User

The header is the account, carrying **Sign out** and the gear (**Manage account**) — there is no
organization to invite anyone to, so signing out takes the slot **Invite** occupies elsewhere, and
there is no account row below to hang it off instead. Being the whole
switcher, the list holds every signed-in account — the active one checked, like the active workspace
above — and nothing else: no workspace rows, no heading, so **Add account** moves to the foot of the
surface the same way **Create organization** does. An organization is active here, and this mode
ignores it entirely, down to the trigger.

## Parts

| Part                | Description                                                                  |
| ------------------- | ---------------------------------------------------------------------------- |
| `UserButtonRoot`    | Owns the data, callbacks, and `mode`; forwards open state to `Popover.Root`. |
| `UserButtonTrigger` | The trigger: the active workspace's avatar, and nothing else.                |
| `UserButtonPopup`   | The popover surface: header, workspace list, additional accounts, footer.    |

## Styling

The component owns no slots of its own — it is styled entirely by the components it composes, so
`appearance.elements` targets those. Overriding `item` re-themes every row here _and_ everywhere else
`Item` is used; that is the point of composing rather than restyling.

| Component | Slots it contributes                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `Popover` | `popover-positioner`, `popover-popup`                                                                                                |
| `Card`    | `card-root`                                                                                                                          |
| `Item`    | `item`, `item-media`, `item-content`, `item-title`, `item-description`, `item-label`, `item-actions`, `item-group`, `item-separator` |
| `Avatar`  | `avatar`, `avatar-image`, `avatar-fallback`                                                                                          |
| `Button`  | `button`                                                                                                                             |
| `Icon`    | `icon`                                                                                                                               |
| `Menu`    | `menu-trigger`, `menu-positioner`, `menu-popup`, `menu-item`, `menu-separator`                                                       |
