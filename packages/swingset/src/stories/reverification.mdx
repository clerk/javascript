## Usage

The feature's model drives the reverification flow around its Clerk call and hands the controller to the feature's controller and view. The component renders nothing while `status` is `idle`. While a challenge is still preparing, the parent card shows a verification header, a centered spinner, and a disabled continue button, then shows the factor without a step transition. Keep the same card around the component for a ready factor, a pending retry, or the error state. Isolated panel stories below are for visual development only.

```tsx
import { Card } from '@clerk/mosaic/components/card';
import { Reverification, useReverificationFlow } from '@clerk/mosaic/features/reverification';

const [runAction, reverification] = useReverificationFlow(action);

<Card.Root renderBranding={false}>
  <Reverification controller={reverification} />
</Card.Root>;
```

## Composing with a parent flow

Reverification is usually one step inside a larger flow, like a confirmation dialog that deletes something. The parent owns the action and decides what is on screen. Reverification only reports whether it has something to show.

### Reading `visible`

`reverification.visible` is true when reverification has a card of its own: a factor, a pending retry, or an error. It is false when idle and while the pending card is showing before a factor is known. A parent that wants to handle pending itself, for example by keeping its own spinner up, can switch to the verification step on `visible` and never render the pending card.

A parent should decide its layout from its own state and `visible`, not from `status`. `status` describes the card, and it changes while the action is still running.

```tsx
const step = isRunning && reverification.visible ? 'verify' : 'confirm';
```

The card covers the wrapped action and nothing more. Work that should happen while the card is up, such as reloading after the mutation, goes inside the action the flow wraps. A parent that has work of its own after the action keeps the step it moved to and leaves `<Reverification>` mounted until it is done, rather than deriving the step from `visible`, which turns false as soon as the action resolves.

### When the run ends

The controller follows the run. When the action resolves or fails, `status` returns to `idle` and `visible` to false. `<Reverification>` keeps showing the last card it rendered, pending and without a way to cancel, for as long as it stays mounted, so a parent that animates the card away does not show an empty card. Gate the card on your own running state and `visible`, as above, so the held card is not shown again before the next run.

A run that never asked for reverification shows no card. `status` stays `idle`, and `visible` stays false for the whole run.

### Cancelling

`reverification.onCancel` is a request. It is undefined when the user cannot cancel, which is the case while the action is being retried. Calling it rejects the action with a `reverification_cancelled` error. The controller returns to `idle` at once and the rejection reaches the parent shortly after, so close from the same handler that calls `onCancel` rather than from the rejection, or the parent's own step can change before it closes.

The parent decides what cancelling means for its own flow. Pass `onClose` to `<Reverification>` to run that instead of `onCancel` when the user presses the Close button on the error card. The parent is then responsible for calling `onCancel` itself, as `Destructive` does when its dialog closes. This lets the parent close or leave the step at the moment of the click, instead of waiting for its own action to unwind.

```tsx
<Reverification
  controller={reverification}
  onClose={() => closeDialog()}
/>
```

### Outcomes

The promise returned by the wrapped action is the outcome. It resolves when the action succeeds, rejects with `reverification_cancelled` when the user cancels, and rejects with the action's own error otherwise. Calling the action while another call is pending rejects with `request_already_in_progress`.
